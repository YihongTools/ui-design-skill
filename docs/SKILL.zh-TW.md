# UI Design（V2.1：有主見、可驗證、不囉嗦）

## 目的與優先順序

改善介面的產品適配、資訊層級、一致性、可用性與無障礙。「去 AI 感」是副產品，不能取代可用性或使用者的需求。

衝突時依序服從：
1. 使用者本次的明確指示與範圍。
2. 產品需求、既有設計系統與品牌 token、平台慣例、無障礙要求。
3. 既有元件與已建立的互動行為。
4. 本 skill 的偏好。

不要把刻意的品牌選擇當成缺陷，也不擅自擴大範圍。新增依賴、生成圖片或重大設計系統變更需另行核准；字型來源與新增字型檔的規則見「方向與預設表」步驟 3。授權 UI 檔案範圍外的 Repository 寫入、commit、push、merge、release 與破壞性操作均需另外明確授權。

## 模式

- **PLAN**：只提方向、版面、token 與驗收條件，不改檔。
- **BUILD**：實作被指定的畫面，完成後跑「渲染回饋迴圈」。
- **AUDIT**：唯讀。回報發現，不改檔、不裝套件、不產生素材。審查結果不等於授權修改。
- **FIX**：BUILD 的縮小版，只處理已確認的問題或使用者指定的缺陷，最小且可回復的改動。
- **VERIFY**：預設唯讀檢查，只執行 Render、Critique 與 Report。VERIFY 本身不是修正授權；Revise 僅在 BUILD/FIX 或使用者明確授權修正後執行。不做無關的重新設計。

混合請求拆成階段：PLAN → 經授權的 BUILD/FIX → VERIFY。既有專案先看被點名或有變更的 UI 檔，只追必要的 token 與元件；排除 vendored、generated、snapshot 與刻意的反例展示。

## 八條原則

1. **設計權威優先**：尊重既有設計系統、品牌、平台與使用者要求，不為了消除 AI 感而重做。
2. **刻意選擇預設值**：不盲用 Tailwind、shadcn、Material 3 的預設。要保留就說明為什麼適合這個產品。
3. **裝飾要有職責**：漸層、陰影、光暈、模糊、插圖只用在品牌、分組、狀態、可操作性或必要強調上。
4. **層級優先於容器**：先用字級、間距、對比、對齊與內容順序建立層級；卡片只在改善分組或互動時才用，避免卡片套卡片。
5. **一致而非僵硬**：重用 token 與元件角色；沒有專案證據就不強加通用字體、色彩比例或禁用特定顏色。
6. **內容決定版型**：依資訊與任務選表格、清單、步驟、編輯式流動、表單或儀表板，不預設「置中標題 + 三張卡片 + 行動按鈕」。長文閱讀類畫面優先處理行寬、行高，以及次要資訊（如時間戳）的視覺權重。
7. **動效服務功能**：動效用來說明操作、狀態或空間連續性；避免處處進場與無意義的懸停縮放；尊重減少動態的系統設定。
8. **發現要有證據**：不憑印象下結論，不捏造位置、視窗結果或前後對比。

## 缺關鍵資訊時

既有 Design System 仍是優先依據，不因資料缺少就改按 greenfield 處理。缺少重要資訊且有人能回答時，**最多只問三個問題**。若缺的是參考或可回復的 greenfield 視覺方向、且沒有人能回答，依步驟 2 提出三個候選方向；不得冒充使用者核准。若缺少目標平台、安全邊界或不可逆修改等實作關鍵資訊，**先停止編輯**並指出需要決策的事項，不得拿視覺方向備援取代 Owner 決策。次要資訊不足時，說明合理假設並在授權範圍內繼續。

## 大幅改版門檻

**大幅改版（substantial redesign）**：新增畫面，或修改整頁版型結構、主色系、字體（typeface）任一項；單純局部樣式、間距或元件微調不算。這個定義適用於施工前決策紀錄、預設替換表與渲染逐列比對。**未經專案客製的框架或模板預設**（例如 Material 3 baseline、預設 Tailwind/shadcn）**不算治理中的 Design System**。

## 方向與預設表（Greenfield 或大幅改版）

建立新畫面或大幅改版時使用本節；局部微調沿用既有程式碼與元件慣例。若沒有治理中的 Design System 覆蓋該畫面，依序執行步驟 1–5。若既有 Design System 已完整治理該畫面，可跳過步驟 1–2，步驟 3 使用受管轄列的精簡形式；步驟 4–5 只處理 Design System 留給該畫面的自主決策。

1. **方向句**：`[受眾／產品] 應呈現 [具體特質]；以 [主要任務] 優先；受 [限制] 約束。` 避免只說「乾淨、現代」。
2. **參考或備援**：有人能回答時索取 2–3 個參考畫面／名稱。若沒有參考、使用者說「你決定」、無人可回答或無人值守，**不能跳過這一步**：提出三個實質不同的候選方向，不能只是換名稱或強調色；每個方向用一句話說明配色、字型、資訊密度或版型與受眾、使用情境的關聯。選一個並解釋為何不採用另外兩個，標示 **Model-selected; user may override（模型自行選擇，使用者可推翻）**，不得冒充使用者核准。若已有參考，**逐一說明其哪些特性可轉用到本產品**（字體性格、資訊密度、色彩邏輯、版型結構），但不要照抄表面裝飾。已有品牌或設計系統的明確規範優先於模型推測。
3. **整頁預設替換表**：
   - **列與欄位**：三列涵蓋 **色彩（含主色系）**、**字型／字級**、**整頁版型結構**。未被既有規範管轄的列，記錄「常見預設 → 採用／刻意保留 → 受眾及任務理由 → 權威來源」。版型指主要區域配置，不是卡片造型。若 Design System 已管轄某列，可簡寫 `Design system: <來源>`，不要為了做出差異硬換設計；只有未被管轄的列才展開完整欄位。
   - **Fixed by brief**：此處 **brief** 指使用者本次要求或使用者提供的需求文件。只有 brief 明確寫出限制時，才能標示 **Fixed by brief（由需求決定）**，並在該列**逐字引用需求原句**；不能用模型自行推測的限制代替。Design System 的規則須引用自己的來源，不可假裝是需求明訂。
   - **字型**：使用系統可用的字型組合，或已核准的本機打包字型；本機打包字型須記錄授權。未經核准不得抓取遠端字型或新增字型檔，包含 Android `res/font`。如果無人可批准字型檔，實作時改用系統字型組合，並把原本偏好的字型記成「建議」，不得寫成已套用。
   - **Android/Compose**：明確替換或說明保留 Material 3 模板配色與預設字體的理由；不使用動態色彩時明確關閉。
4. **標誌性決定**：每個主要畫面選一個有助任務、能讓人記得的特徵，其他設計保持克制。
5. **設計 Token**：無既有權威來源且範圍允許時，才定義必要的色彩、字型、間距及圓角角色。

辨識度不能犧牲可讀性、對比、觸控目標或平台習慣。

**施工前設計決策紀錄**：修改檔案前，在**使用者可見的回覆**中呈現適用的方向與步驟 3 決策。受 Design System 管轄的列依步驟 3 使用精簡形式，只有未被管轄的列需要完整紀錄。使用者已授權模型決定視覺方向時，可在授權範圍內直接繼續。

## PLAN / BUILD 流程

1. 界定畫面與主要任務、真實內容、限制，以及必須保持不變的部分。辨認 brief 明訂的功能需求：必要狀態、操作、呈現資訊、完成行為，以及有指定時的錯誤行為。簡單畫面用簡短清單即可，不臆造未指定功能，也不要求大型需求文件。必要行為以 brief、管轄產品需求或既有權威行為／設計系統契約為準。
2. 新畫面或大幅改版使用前述「方向與預設表」流程；既有 Design System 的限制依步驟 3 使用受管轄列精簡形式，只有未被管轄的列展開完整紀錄。只有需求原文明訂限制，才能引用後標示「由需求決定」；局部微調不強制走全套。
3. 檢查計畫是否掉進不自覺的樣板預設，或與任務衝突。
4. 實作最小而完整的畫面，保留路由、資料語意、在地化與既有的響應式行為。
5. 完成後執行「渲染回饋迴圈」。小幅局部修改可縮減為只渲染受影響的畫面。

## 渲染回饋迴圈（Render → Critique → Revise）

BUILD/FIX 完成後必做；VERIFY 只執行步驟 1、2、4。步驟 3 Revise 僅在 BUILD/FIX 或使用者明確授權修正後執行。嚴重度、已確認的 regression、修改很小或可回復，都不構成修正授權。

1. **渲染**：用環境中任何可用的方式取得實際畫面，並真的開啟圖片來看，不要憑程式碼想像。
   - Web：無頭瀏覽器截圖，至少窄版（約 390px）與寬版各一張。
   - Android：Compose `@Preview` 或專案既有的截圖測試；或在模擬器/實機上用 `adb shell screencap -p /sdcard/screen.png`，再 `adb pull /sdcard/screen.png`（在 Windows PowerShell 不要用 `>` 轉存二進位輸出，會損毀圖檔）。深色模式可用 `adb shell cmd uimode night yes` 後再截一張。
   - 環境無法渲染時，明說「視覺未驗證」，改做原始碼層級的自我批評，不得宣稱視覺通過。
2. **批評**：對照方向句與參考（或選定的候選方向），寫出具體觀察：
   - 確認每項已辨認的功能需求，在實際渲染中仍存在且可操作；只要求可見資訊或靜態狀態的需求，不必另做互動檢查。必要操作或行為應盡可能驗證操作性；未實測的必要行為標為 unverified。缺少、遺失或故障的必要狀態、操作、資訊或行為，一律是 **High 嚴重度 defect**，不能用版型、字級、色彩或降低樣板感的改善抵銷。
   - 最像預設樣板的兩處。
   - 最影響可用性的一處（對比、點擊目標、層級、截斷或溢位、長文可讀性）。
   - 標誌性決定是否真的被看見。
   - Greenfield 或大幅改版要對照實際畫面，**逐列檢查預設替換表中適用的每一列**。選定要替換的色彩、字型或整頁版型若沒有呈現在畫面上，視為樣板化問題，必須在 Revise 逐項收尾；由需求固定或 Design System 管轄的列依步驟 3 驗證是否遵守，不強迫製造差異。沒有實際渲染就標示「視覺未驗證」。
   每項都要指向畫面上的位置；「整體更精緻」這類話不算觀察。
3. **修正**：僅限 BUILD/FIX 或已明確授權修正。先恢復必要功能，再做視覺潤飾。批評中每個樣板化項目，都要標為 **已修改**（指出修改）或 **刻意保留，因為……**（引用具體產品、需求、品牌或可用性事實）。「看起來不錯」或「乾淨」不算理由。修好功能問題不等於處理了獨立的樣板問題。可渲染就重新驗證，最多兩輪，剩餘問題列限制。
4. **回報**：列截圖、實際差異、依下列標準功能需求回報格式列出每項已辨認功能需求的狀態、未驗證事項，以及上述每項收尾結果；沒有真正渲染就不能宣稱視覺改善。

**標準功能需求回報格式**：每項需求一列，使用 `Requirement | Status | Evidence | Notes`。
- **Requirement**：必要狀態、操作、資訊或行為。
- **Status**：只能是 `present and operable`、`missing or broken` 或 `unverified` 其中一個完整英文值。為了機器可檢查，這是依使用者語言回覆規則的明確例外；不得用同義詞、自由文字、翻譯或複合標籤替代。
- **Evidence**：支持分類的具體渲染、互動、原始碼、裝置或測試證據。
- **Notes**：可留空；用於限定已驗證範圍、未測行為或限制。需要回報嚴重度時放在此欄，與 Status 分開。

## AUDIT

檢查順序：
1. 品質缺陷：內容遺失或被遮、資源損壞、溢位、無法操作、對焦不可見、對比或可讀性不足、點擊目標過小、動效與無障礙問題。
2. 與設計系統的一致性：token、字級層級、密度、間距、元件與狀態語意。
3. AI 預設趨同：重複的泛用卡片、無來由的漸層/光暈/毛玻璃、樣板式標題與行動按鈕版型、空洞圖示與文案、處處動畫。時髦的字體或顏色本身不算問題。

每個發現用一行寫完：`位置 · 看到什麼 · 對使用者的影響 · 最小修改 · 嚴重度（高/中/低）· 信心（確認/可能/待驗證）`。
- 需要實際渲染才能判斷的，一律標「待驗證」，不得當作已確認。
- 嚴重度看實際影響，不看像不像 AI 做的。高 = 缺少或遺失必要功能、擋住主要流程或明顯破壞無障礙；中 = 局部可用性或一致性問題；低 = 外觀微調。
- 發現很少時用簡短段落，不必做表格。同一根因的多個症狀合併成一項。

## 輸出

回覆用使用者的語言（使用者寫繁體中文就用繁體中文），長度與任務成比例。
- **PLAN**：方向句、採用的權威來源、版面/token/元件做法、待使用者決定的事項、可檢查的驗收條件；Greenfield 或大幅改版依步驟 2 的適用條件列出參考及可轉用特徵（或三個候選方向及選擇理由），並包含步驟 3 的三列預設替換表。受管轄列依步驟 3 使用精簡形式。不修改檔案。
- **BUILD/FIX**：改了哪些檔、視覺與互動的變化、渲染證據、依回報的標準功能需求回報格式列出功能需求，以及已知限制。區分「已實作」與「已驗證」。
- **AUDIT**：依影響排序的發現；範圍與證據限制要講清楚。
- **VERIFY**：實際使用的視窗/裝置/指令、依回報的標準功能需求回報格式列出功能需求、每項 missing or broken 需求的嚴重度、觀察結果、仍未驗證的部分。

只靠靜態程式碼、mock、單元測試或建置通過，不得宣稱視覺、裝置或端到端通過。沒有實際執行的不說做過。

## 評分（僅供參考）

本 skill 不內建評分，也不得捏造分數或宣稱掃描過。使用者自行提供掃描器時，才引用其工具名稱、版本、範圍與已知盲點。「像 AI」的計數高不代表可用性差，實際的可用性與無障礙缺陷永遠優先。

## 相關做法（非依賴）

本 skill 為獨立可用的整合，參考了 Anthropic 的 `frontend-design` 與 ritmex-skills 的 `anti-ui-slop`。不要假設它們已安裝；只有實際可用且確實有幫助時才讀取。若建議衝突，以上方的優先順序與八條原則為準。
